# Зміст

# 1. Види тестування, що застосовуються до системи
## 1.1. Відповідність реалізації системи технічному завданню (SRS)
Кожна вимога розділу 3 SRS перевіряється на наявність реалізації та коректність роботи.
## 1.2. Функціональне тестування
Перевіряється відповідність функцій системи вимогам SRS та бізнес-логіці клубу: управління користувачами, клієнтами, тренерами, розкладом, записом, абонементами, оплатами, відвідуваністю та звітами.
### Відповідність елементів управління бізнес-даним
- коректність введення, збереження, редагування та видалення даних клієнтів і тренерів;
- правильність форматів: email (унікальний), телефон (лише цифри та + - ( ), 10–13 цифр), дата і час заняття;
- неможливість введення некоректних даних (символи у числові поля, невірний формат);
- неможливість дублювання email (повторна реєстрація → 409);
- обов'язковість ключових полів (ім'я, email, пароль, телефон; для заняття — дата, час, тренер, місткість).
### Відповідність дій бізнес-правилам
- неможливість запису на тренування без активного абонемента;
- неможливість запису, якщо всі місця зайняті (booked ≥ max_clients);
- неможливість повторного запису того самого клієнта на те саме заняття (UNIQUE);
- неможливість створення заняття без обов'язкових полів та з тренером невідповідної спеціалізації;
- видалення клієнта виконується каскадно разом із його абонементами, записами та відвідуваннями (ON DELETE CASCADE);
- заборона видалення плану абонемента, що використовується у виданих абонементах (порушення FK → 409);
- ціна плану та сума оплати — лише додатні (CHECK price>0, amount>0); дата кінця абонемента > дати початку.
### Перевірка роботи відповідно до ролей
- адміністратор — повний доступ (користувачі, клієнти, тренери, розклад, абонементи, оплати);
- керівник/менеджер — аналітичні звіти та фінансові показники;
- тренер — власний розклад, списки клієнтів, фіксація відвідуваності;
- клієнт — перегляд розкладу, запис на тренування, стан власного абонемента;
- користувач не має доступу до функцій інших ролей (403).
### Цілісність і транзакційність
- пов'язані операції виконуються в одній транзакції (реєстрація: users+clients; бронювання: перевірка+вставка) — або всі, або жодна;
- при збої транзакція відкочується без часткового запису.
### Unit-тести (для функцій бізнес-логіки)
- перевірка логіна/пароля (bcrypt.compare) та формування/верифікація JWT;
- перевірка ролі користувача та доступних прав (requireRole);
- перевірка наявності вільних місць на занятті (booked < max_clients);
- валідація телефону та плану абонемента (ціна, тип, тривалість/кількість занять);
- розрахунок суми оплат за період для звітів.
## 1.3. Тестування бази даних
- перевірка форматів зберігання (numeric(10,2) для сум, date, varchar з обмеженням довжини);
- перевірка первинних ключів, індексів та зовнішніх ключів між таблицями PostgreSQL;
- перевірка каскадних правил: ON DELETE CASCADE (clients, bookings), ON DELETE SET NULL (schedules.trainer_id, subscriptions.plan_id);
- неможливість видалення рядків, на які посилаються FK без каскаду (план абонемента);
- дотримання CHECK-обмежень (role, price>0, amount>0, max_clients>0, end_date>start_date) та значень за замовчуванням.
## 1.4. Тестування інтерфейсу користувача
- відповідність єдиному стандарту оформлення, шрифтів та кольорової гами;
- коректне відображення на ПК, планшеті та смартфоні; робота на моніторі від 800×600;
- робота з елементами керування мишкою і клавіатурою; коректний порядок обходу по Tab;
- відповідність мови написів (українська); поява скролбарів; зміна ширини колонок у таблицях;
- підказки (tooltips), повідомлення про помилки при некоректному введенні;
- підтвердження перед видаленням важливих даних; індикатор завантаження для тривалих операцій;
- фільтрація, пошук і сортування даних у таблицях; час реакції форм ≤ 2 с.
## 1.5. Конфігураційне тестування
- робота клієнтської частини PWA у сучасних браузерах (Chrome, Firefox, Edge);
- запуск серверної частини в середовищі Node.js та взаємодія з PostgreSQL;
- встановлення залежностей через npm; наявність і коректність файлу .env;
- працездатність PWA-компонентів (manifest.json, Service Worker, встановлення застосунку);
- неможливість роботи при невідповідності версій клієнта, сервера або БД.
## 1.6. Тестування звітів
- формування зведеного звіту, звіту відвідуваності, звіту по персоналу та оплатах;
- визначення вхідних параметрів (діапазон дат) і значень за замовчуванням;
- відповідність заголовка звіту обраним параметрам; мономовність;
- правильність підсумкових сум; відсутність помилок округлення; адекватна точність;
- узгодженість чисел у логічно пов'язаних звітах (сума у зведеному = деталізованому).
## 1.7. Тестування підсистеми адміністрування
- створення та редагування користувачів; призначення ролі (admin/manager/trainer/client);
- відповідність доступних функцій ролі; заборона доступу клієнта до адмінфункцій (403);
- заборона доступу тренера до керування оплатами/фінзвітами;
- коректність автентифікації; завершення сеансу при виході (відкидання токена).
## 1.8. Тестування навантаження та продуктивності
- PR-1: середній час відповіді ≤ 2 с, максимальний ≤ 5 с;
- PR-2: пропускна здатність ≥ 50 запитів/с; PR-3: ≥ 200 одночасних користувачів, ≥ 10 000 клієнтів у БД;
- PR-4: у режимі деградації час відповіді ≤ 7 с без втрати даних; PR-5: CPU ≤ 70 %, без витоків пам'яті;
- оцінка приросту БД та робота на великих обсягах даних; пул з'єднань PostgreSQL (до 10).
## 1.9. Інтеграційне тестування
- взаємодія PWA ↔ REST API (Node.js/Express) ↔ PostgreSQL;
- повний цикл: реєстрація → абонемент → запис → відвідування → оплата → звіт;
- оновлення даних у кабінеті клієнта/розкладі тренера після змін адміністратором;
- одночасне виконання бронювань кількома клієнтами (контроль race condition через транзакцію).
## 1.10. Тестування надійності та відмовостійкості
- RR-1: доступність ≥ 99 % (робота 24/7); RR-3: відновлення після збою (MTTR ≤ 1 год);
- робота клієнта після короткочасної втрати з'єднання та після перезавантаження сервера/БД;
- збереження цілісності даних після аварійного завершення операції (відкат транзакції);
- відсутність дублювання записів після повторного виконання операції; повідомлення про недоступність сервера.
## 1.11. Тестування інсталяції / оновлення версії
- безпомилкове встановлення залежностей (npm) та запуск сервера (npm start);
- безпомилкове виконання SQL-міграцій (npm run db:migrate); збереження наявних даних після оновлення;
- наявність необхідних файлів постачання (manifest.json, Service Worker, .env);
- наявність опису нової функціональності та актуальність експлуатаційної документації.
## 1.12. Приймальне тестування
Перевірка критично важливих сценаріїв: вхід і розмежування доступу за ролями, ведення клієнтів, створення розкладу, запис на тренування, оформлення абонемента, внесення оплати, фіксація відвідуваності та формування звітів. Якщо систему не пройдено за цими сценаріями — складання не оголошується версією. Доцільно залучати представника замовника; результати оформлюються протоколом, що додається до версії.
# 2. Порядок тестування
## 2.1. Дії до тестування
- тестування проводиться на тестовій БД, відокремленій від середовища розробника (копія реальної);
- підготувати контрольні дані: користувачів усіх ролей, клієнтів, тренерів, заняття, абонементи, оплати, записи (npm run db:seed);
- виконати міграції, запустити сервер (npm start), перевірити працездатність REST API та відкрити PWA у браузері;
- підготувати таблиці тестів і форму опису знайдених помилок.
## 2.2. Дії при виявленні дефекту
Дефект заноситься до системи управління задачами Jira із зазначенням:
- коду/номера помилки та номера тесту, під час якого виявлено;
- підсистеми/функції, де виникла помилка; версії продукту;
- рівня важливості (див. п. 2.4); опису та послідовності дій для відтворення;
- очікуваного й фактичного результату; скріншотів та фрагментів журналу.
## 2.3. Дії після тестування версії, що виставляється замовнику
- заповнити та затвердити протокол внутрішніх випробувань версії;
- підготувати документи для передачі версії замовнику;
- провести експлуатаційні випробування версії у замовника.
