# Аудит бази даних OLIMP (sports_club_db)

**Дата аудиту:** 17.07.2026
**Обсяг:** schema.sql + 21 міграція + всі серверні маршрути (5 632 рядки коду перевірено на реальне використання полів)

---

## Як я зрозумів систему

Система керування спортклубом з 4 ролями (admin, manager, trainer, client). Ядро: `users` (автентифікація) → доменні таблиці `clients`/`trainers` (1:1 до users). Клієнти купують абонементи (`subscriptions` за шаблонами `subscription_plans`), записуються на заняття (`bookings` → `schedules` → `workouts` + тренер), відвідують клуб (`visits`). Фінанси — `payments`. Комунікації: оголошення (`messages` + адресати + прочитання), живий чат гість↔адмін (`chat_*`), 2FA (`email_codes`, `pending_registrations`), нотатки тренера про клієнтів (`trainer_client_notes`), антропометрія (`client_anthropometry`), налаштування клубу (singleton `club_settings`).

Бізнес-логіка, підтверджена кодом: скасування броні = фізичний DELETE; візити створює адмін вручну; протермінування абонементів — UPDATE при запитах; оплата створюється разом з підпискою.

## 2. Критичні проблеми

### П1. Телефон зберігається у ТРЬОХ місцях `users.phone`, `clients.phone`, `trainers.phone`
- **Де:** users (міграція 015), clients (початкова схема), trainers (міграція 002)
- **Чому проблема:** одна й та сама інформація (контакт людини) у трьох колонках. Код читає непослідовно: `users.js` робить `coalesce(c.phone, t.phone)` (ігнорує users.phone), `reports.js:215` читає `u.phone as trainer_phone` — **це активний баг**: телефони тренерів лежать у `trainers.phone`, тож звіт по тренерах показує порожній телефон.
- **Сценарій прояву:** клієнт оновлює телефон у профілі → пишеться в clients.phone; адмін дивиться звіт → там users.phone (порожній або застарілий). Дані суперечать одне одному.
- **Виправлення:** консолідувати в `users.phone` (телефон — атрибут людини, не ролі); мігрувати дані `coalesce(clients.phone, trainers.phone) → users.phone`; дропнути колонки в clients/trainers; оновити ~15 запитів.
- **Пріоритет: ВИСОКИЙ** (баг у звітах уже зараз)

### П2. Скасування бронювання = фізичний DELETE, історія знищується
- **Де:** `bookings.js` router.delete — `delete from bookings where id = $1`
- **Чому проблема:** у коді існує константа `BOOKING_STATUS.CANCELLED`, у таблиці є поле `status`, але воно завжди `'active'` — скасування видаляє рядок. Втрачається: хто записувався і скасовував, статистика популярності занять, а головне — **запланована функція авто-відмітки відвідувань** («клієнт не скасував до початку → visited») потребує історії броней з часом скасування.
- **Сценарій прояву:** клієнт записався і скасував 10 разів — жодного сліду; тренер каже «у мене був запис» — довести неможливо.
- **Виправлення:** замість DELETE — `update bookings set status='cancelled', cancelled_at=now()`. У запитах підрахунку місць уже стоїть фільтр `b.status = 'active'` (bookings.js:169,185) — тобто **код читання вже готовий** до цього; поміняти треба лише DELETE-хендлер. UNIQUE(client_id, schedule_id) замінити на частковий унікальний індекс `WHERE status='active'`, щоб клієнт міг перезаписатися після скасування.
- **Пріоритет: КРИТИЧНИЙ** (незворотна втрата даних + блокує заплановану функцію)

### П3. Немає CHECK-обмежень на статуси `subscriptions`, `bookings`, `payments`
- **Де:** всі три таблиці: `status varchar(20) NOT NULL DEFAULT ...` без CHECK
- **Чому проблема:** код оперує фіксованими наборами (`active|paused|expired|cancelled`, `active|cancelled`, `completed|pending|refunded`), але БД прийме будь-який рядок — `'aktive'`, `'ACTIVE'`, `''`. Такий рядок випадає з усіх фільтрів мовчки.
- **Сценарій прояву:** одрук у майбутньому коді або ручний UPDATE у DBeaver → абонемент «зникає» з інтерфейсу, клієнта не пускають.
- **Виправлення:** додати CHECK-и (SQL нижче). У workouts, plans, messages, chat_messages CHECK-и вже є — це і є прийнятий у проєкті стиль.
- **Пріоритет: ВИСОКИЙ**

### П4. `payments` без точного часу і без аудиту
- **Де:** payments має лише `date` (день), немає `created_at`
- **Чому проблема:** фінансові записи повинні мати точний момент створення. Дві оплати одного дня неможливо впорядкувати; звірка з банком/касою неможлива.
- **Виправлення:** додати `created_at timestamptz NOT NULL DEFAULT now()`. Поле `date` лишити (бізнес-дата оплати може відрізнятись від моменту вводу).
- **Пріоритет: ВИСОКИЙ**

### П5. `visits` не пов'язані з заняттями/бронями
- **Де:** visits(client_id, subscription_id, visit_time) — міграція 020 видалила мертву колонку schedule_id
- **Чому проблема:** видалення тоді було правильним (колонку ніхто не заповнював). Але запланована функція авто-відмітки відвідувань потребуватиме зв'язку visit→schedule (яке саме заняття відвідано). Зараз «відвідування заняття» неможливо відрізнити від «просто прийшов у зал».
- **Виправлення:** при реалізації авто-відмітки повернути `schedule_id int4 NULL REFERENCES schedules(id) ON DELETE SET NULL` (NULL = звичайний вхід у зал) — цього разу з кодом, що її заповнює.
- **Пріоритет: СЕРЕДНІЙ** (до моменту реалізації функції)

### П6. Разові абонементи (usage_count) не обліковуються
- **Де:** subscription_plans.usage_count існує, але жодне місце коду не рахує використання візитів проти ліміту
- **Чому проблема:** «Разове відвідування залу» (usage_count=1) після 1 візиту лишається active до end_date. Клієнт може ходити безлімітно.
- **Сценарій прояву:** клієнт купив разове за 150 грн і ходить місяць.
- **Виправлення:** або тригер/запит: при insert у visits порахувати `count(visits) >= usage_count` → перевести підписку в 'expired'; або view з обчисленим залишком. Мінімум — реалізувати перевірку в visits.js POST.
- **Пріоритет: ВИСОКИЙ** (пряма втрата грошей клубу)

### П7. `chat_conversations` прив'язка до користувача магічним рядком
- **Де:** guest_token = `'client-<userId>'` для авторизованих (chat.js:62-64)
- **Чому проблема:** зв'язок з users закодований у текстовому токені, а не FK. Видалення користувача не чіпає діалог (осиротілий токен); JOIN до users неможливий без парсингу рядка; теоретична колізія з guest-токеном такого ж вигляду.
- **Виправлення:** додати `user_id int4 NULL REFERENCES users(id) ON DELETE SET NULL`, заповнити з токенів, використовувати для авторизованих. guest_token лишити гостям.
- **Пріоритет: СЕРЕДНІЙ**

### П8. `trainer_client_notes.client_id` без індексу
- **Де:** UNIQUE(trainer_id, client_id) покриває лише префікс trainer_id; новий ендпоінт `/client-notes-all/:clientId` фільтрує за client_id
- **Виправлення:** `CREATE INDEX ON trainer_client_notes(client_id)`.
- **Пріоритет: НИЗЬКИЙ** (таблиця мала, але індекс FK — правило)

### П9. `messages.status='planned'` не обробляється
- **Де:** статус і send_date зберігаються, але жоден планувальник не переводить planned→sent
- **Чому проблема:** адмін планує розсилку на дату — вона ніколи не «відправиться» (не з'явиться у сповіщеннях), бо notifications.js фільтрує лише sent.
- **Виправлення:** або cron-перевірка (як протермінування підписок — при запитах), або прибрати функцію планування з UI.
- **Пріоритет: СЕРЕДНІЙ** (функція мовчки не працює)

## 6. Дублікати та зайві сутності

**Дублюється:**
- `phone` × 3 (П1) — єдиний справжній дублікат даних у схемі.

**Можна видалити:**
- `clients.phone`, `trainers.phone` — після консолідації.
- `trainer_client_notes.id` — опційно (замінити складеним PK).

## 9. План міграції (безпечний, покроковий)

Стиль проєкту — ідемпотентні міграції, що запускаються при старті (migrate.js). План розбитий на 3 незалежні міграції, кожна безпечна для повторного запуску і не ламає роботу поточного коду між кроками.

### Міграція 021 — обмеження та колонки (без зміни коду)
```
1. ALTER payments  ADD created_at timestamptz NOT NULL DEFAULT now();
2. ALTER bookings  ADD created_at timestamptz NOT NULL DEFAULT now();
3. ALTER bookings  ADD cancelled_at timestamptz NULL;
4. ALTER subscriptions/schedules/users/clients/trainers ADD created_at (той самий патерн);
5. CHECK-и на статуси — через DO $$ блок: додаються лише якщо всі наявні
   значення валідні, інакше NOTICE (стиль міграції 020);
6. CREATE INDEX IF NOT EXISTS idx_trainer_notes_client
   ON trainer_client_notes(client_id);
```
**Відкат:** DROP COLUMN / DROP CONSTRAINT — дані не втрачаються.

### Міграція 022 — статусна модель бронювань (код і БД разом)
```
1. UNIQUE(client_id, schedule_id) → частковий унікальний індекс:
   DROP CONSTRAINT bookings_client_id_schedule_id_key;
   CREATE UNIQUE INDEX bookings_active_unique
     ON bookings(client_id, schedule_id) WHERE status = 'active';
2. Код bookings.js: DELETE-хендлер → UPDATE status='cancelled',
   cancelled_at=now() (для клієнта); адмін DELETE лишити для виправлення помилок вводу.
3. Перевірка: підрахунок місць уже фільтрує status='active' — регресії немає.
```
**Відкат:** повернути звичайний UNIQUE (спершу видаливши cancelled-дублікати), повернути DELETE.

### Міграція 023 — консолідація телефонів
```
1. UPDATE users u SET phone = coalesce(u.phone, c.phone)
   FROM clients c WHERE c.user_id = u.id AND u.phone IS NULL;
   -- те саме з trainers
2. Оновити код (6 файлів): всі читання/записи phone → users.phone;
3. Тиждень паралельної роботи (старі колонки ще на місці, але не пишуться);
4. Перевірка: SELECT count(*) FROM clients WHERE phone IS DISTINCT FROM
   (SELECT phone FROM users WHERE id = user_id) — має бути 0 нових розбіжностей;
5. Лише після перевірки: ALTER TABLE clients DROP COLUMN phone;
   ALTER TABLE trainers DROP COLUMN phone.
```
**Відкат до кроку 5:** тривіальний (колонки на місці). Після 5 — відновлення з бекапу.

### Окремо, при реалізації відповідних функцій

- chat_conversations.user_id — разом з рефакторингом chat.js;

## Відкриті питання до власника системи

Усі 4 пункти вирішено.

1. **Чи видаляють клієнтів фізично?** Вирішено (міграція 026): `subscriptions.client_id` переведено з CASCADE на SET NULL — так само, як уже зроблено для payments (020) і visits (024). Підписка видаленого клієнта лишається в зведеній аналітиці (reports.js: planStats рахує по плану, не по клієнту), але зникає з клієнт-орієнтованих списків (INNER JOIN clients) — так само, як уже поводяться payments і visits. RESTRICT не обрано: майже кожен клієнт має підписку, тож видалення клієнта з адмінки перестало б працювати взагалі.
2. **Візити:** власник підтвердив — кілька візитів клієнта на день допустимі. Унікальний індекс НЕ додається, поведінка лишається без змін.
3. **Антропометрія:** CHECK-межі додано (міграція 021) — широкі, безпечні діапазони (вага 0–400 кг, зріст 40–260 см тощо), що відсікають лише явні одруки й не звужують легітимні значення.
4. **messages 'planned':** реалізовано (міграція коду не потребувала) — лазива активація `planned → sent` за настанням `send_date`, за тим самим патерном, що й протермінування абонементів (`subscriptions.js`).
